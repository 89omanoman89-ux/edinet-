# P4: 既存ローカル市場データとの保守的PIT結合

P3の固定primary 35書類とrevision_support 14書類だけを使用する。
P0–P3の実装、P2標本、原本、過去snapshotを変更しない。対象を成功した書類に入れ替えない。
今回のP4はデータ結合と検証に限定し、backlogにあるリターンラベル・コスト・評価は実装しない。
P5、バックテスト、ランキング、仮説探索、全市場展開は対象外。

## 実装と採用条件（最初のinterval経路）

この節から旧受入結果までは`p4-pit-market-v1`の記録。下記の直接観測経路は、このinterval推測を行わず別定義で採用する。

- `jquants_local.py`: Git外の既存CSV/GZIPと保存済みmanifestをread-onlyで検査する。各datasetでrevisionが複数あれば任意に最新版を選ばず拒否する。
- `pit_market.py`: 時点付き証券mapping、日次session、価格の公開時刻、P3 `as_of`を検査するカーネル。
- `p4_audit.py`: P3固定標本を起点に対象ファイルを先に固定し、新規の私有snapshotへ監査結果を保存する。
- `registry/p4_contract_v1.json`: 時点・価格basis・識別子・比較の定義版と参照仕様。

entity、filer/issuer/subject、security、code、有効期間、上場期間、提供者の行、取引sessionを分ける。
codeは4/5文字の文字列で、英字・先頭ゼロを保持する。名前join、末尾切捨て、補完は禁止。
日付付きmaster行とEDINET提出metadataのcodeが等しくても、issuer関係や有効期間の証明へ自動昇格しない。
複数候補、期限不明、上場境界不明、判断時点以降にしか利用できないmappingはBLOCKED。
code変更・再利用時には価格観測日にも同じsecurityとの対応が有効でなければ採用しない。

正のカーネル入力には、明示的に検証された有効期間・上場期間・issuer関係・公開時刻と、
hash/行locator付きmapping証跡が必要。証跡の書式検査だけで主張の真実性を認証するものではない。
P3原本逆引き済みfact IDと、J-Quantsバイト・CSV行再読済みobservation IDも別々に要求する。
現在のローカルCSV用adapterは、この追加証跡がない候補をBLOCKEDのまま出力する。
任意の自己申告JSONをPASSのmappingとして取り込むCLIは設けていない。

## 時間と価格

監査のdecisionは各書類のP3公開時刻上限の1 microsecond後。P3の訂正系列・競合・nullをそのまま使う。
calendarに全日付が存在することを確認し、公開時刻とdecisionより厳密に後に始まる最初の**日次barのsession**を候補とする。
日次データだけなので、場中・引け後開示は次の取引日の開始へ進む。午前開示に同日午後の価格を割り当てない。
休日とOSEだけの祝日取引日は東証現物のsessionとしない。欠落日を平日規則で生成しない。
半日取引の時間が未確認ならBLOCKED。session予定と実際の約定を区別し、`execution_claim=false`とする。
正のjoinではcalendarの採用版も判断時点より前に公開済みと確認できなければBLOCKED。
現在取得済みのcalendarで候補日を観測することと、当時の版の利用可能性を分ける。

正のjoinには、entry候補時点の売買可否を判断時点までに確認した証跡も要求する。
売買停止・売買可否不明・上場廃止・価格なしを黙って除外して次の好都合な価格へ進まない。
価格featureは判断日の前日以前の、対象codeで最新の報告終値だけを候補とする。
観測日を保持し、当日終値や未来のentry価格をfeatureへ入れない。公開時刻が不明なら採用しない。

非調整価格と元の`AdjFactor`/`ExRT`を別々に保持する。将来の分割を過去価格へ反映しない。
調整済み価格の版が不明、または判断時点以降なら拒否する。既知版の調整済み価格も今回の採用範囲外。
価格×株数、配当込みreturn、CFO-CapEx等を作らない。EPS/BPS/株数の調整basisが未確認なら定義差として残す。

## 独立した財務sourceの比較

J-QuantsのFY実績だけを、小さな明示的field定義で比較候補にする。予想・四半期・未確認定義は台帳へ残す。
期間、flow/instant、scope、会計基準、unit、share basis、公開時刻、訂正を照合する。
IFRSのEq/BPS等は意味を推測してP3 metricへ割り当てない。EDINET訂正はrevision_differenceを保持する。
分類はexact_match / timing_difference / definition_difference / scope_difference /
accounting_standard_difference / revision_difference / value_conflict / unresolved。
identity未確認なら数値一致を認証しない。時刻適格性とidentity適格性を別々に記録する。
J-Quantsの報告時刻はCSV内の開示時刻であり、保存済み版の当時の配信・取得成功とは扱わない。
独立sourceのIDを維持し、P3のBLOCKED・unknown mapping・訂正nullをJ-Quantsで埋めない。

## 公式仕様との対応

- [master](https://jpx-jquants.com/en/spec/eq-master): 日付付き観測。名前一致をissuer証明に使わない。
- [日足](https://jpx-jquants.com/ja/spec/eq-bars-daily) / [bulk調整](https://jpx-jquants.com/ja/spec/eq-bars-daily/adj): bulkの非調整価格と調整係数を分離。NULL価格だけでは売買停止理由を特定できない。
- [calendar](https://jpx-jquants.com/ja/spec/mkt-cal) / [休日区分](https://jpx-jquants.com/ja/spec/mkt-cal/holiday-division): 日付と区分を観測し、時刻を捏造しない。
- [財務](https://jpx-jquants.com/ja/spec/fin-summary) / [書類種別](https://jpx-jquants.com/ja/spec/fin-summary/typeofdocument): 開示日/時刻・元field・決算期・scopeを維持。
- [東証取引時間](https://www.jpx.co.jp/equities/trading/domestic/01.html) / [2024年延長](https://www.jpx.co.jp/corporate/news/news-releases/1030/20230920-01.html): 2016年以降の全日開始09:00、2024-11-05から終了15:30、それ以前15:00という限定rule。予定sessionであり約定証明ではない。

### Identity / listing

[EDINET API仕様書](https://disclosure2dl.edinet-fsa.go.jp/guide/static/disclosure/download/ESE140206.pdf)の3-1-2-2、項目14/15（印刷p.46）は、
`edinetCode`と`secCode`を提出者の識別子と定義する。P3にコピーされた文字列だけに依存せず、元の日次JSONのバイトhash・日付・seqNumber・元行を再読して確認する。
今回は有報120・訂正130の提出者自身の証券codeに限り、fund/subject/別issuerとの混同を拒否する。

そのexact codeで、価格日・decision日・entry候補日のそれぞれに、exact Dateのmaster行が一つあることを要求する。
4/5文字を補完・切捨てしない。各行のDate、Code、ProdCat、Mkt/MktNm、file/row hashとlocatorを保存する。
商品区分011（内国株券）と確認済み東証市場区分だけを採用し、ETF・REIT・外国株・未知区分は今回BLOCKED。
011は優先株も含むため普通株と断定しない。名前はjoinに使わない。

`direct_dated_listing_observation`は**その日だけの観測**であり、上場開始日・廃止日や日付間の継続上場を意味しない。
security IDにも観測日集合を含め、未観測期間へ接続しない。どれかの日にcodeが違う、行がない、複数候補がある場合はBLOCKED。
固定対象のEDINET証跡内で、判断時点までに同じcodeの異なる提出主体が確認されれば、code再利用/主体矛盾としてBLOCKED。
これは全期間・全市場のcode再利用検出を完了したという意味ではない。未来の提出者情報を過去の判定へ混入させない。

### 証拠レベルと時間

定義には次の5レベルを用意し、同一の「取得済み」へまとめない。

| evidence level | 用途 |
|---|---|
| observed_historical_acquisition | 当時の取得ログを検証できる場合だけ。今回のJ-Quantsでは使用しない |
| official_provider_schedule_reconstruction | 公式仕様から再構成した価格利用時刻 |
| direct_dated_observation | 元EDINET metadataと対象日masterによるidentity/listing |
| current_reconstruction | 保存済みcalendarによる予定session、entry後の取引観測 |
| unknown | チャネル・公開時刻・版を確認できないもの |

価格の利用規則は、[提供データの更新タイミング](https://jpx-jquants.com/ja/spec/data-update)の株価日次更新と、
[CSVダウンロード](https://jpx-jquants.com/ja/spec/bulk)の当日配信データ提供を併せたもの。
bulk取得と確認できる非調整日足について、同日16:30頃というdatasetの予定時刻をそのまま精密時刻として扱わず、
翌暦日00:00 JSTを採用時刻とする。これは**公式scheduleを使う本実装の保守的な日単位再構成規則**であり、
提供者が保証した配信上限ではない。仕様自身も更新時刻が前後し、変更され得ると説明している。
未知チャネルにRESTや機関投資家向けSFTPの時刻を流用しない。

実際の取得チャネルは、元manifestのmode/endpoint、保存済みbulk一覧のhash、file key/size、raw hashの対応で確認する。
公開時刻規則の対象は元の日足観測であり、後年再生成された月次CSVオブジェクトが過去に存在したとの主張ではない。
現行の仕様によるpublic reconstructionで、当時の同一版配信・取得・サービス提供履歴の再現ではない。
URL、仕様API版、確認日、取得した仕様バイトhash、適用ruleを保存する。unversionedなWeb仕様に架空のrelease番号を付けない。
元の取得時刻・provider版が不明ならnullを維持し、system replayはNOT ESTABLISHED。

直前のcalendar営業日に価格行がなければBLOCKED。古い好都合な価格へ探し直さない。
価格日がdecision日より前、再構成した利用時刻がdecisionより厳密に前、非調整価格であることを検査する。
財務・株数・価格の補完、調整済み価格、return計算は追加しない。

### decision / entry予定 / outcomeの分離

`decision_information`にはPIT EDINET fact、既知の過去価格、提出者証跡、価格日・decision日の直接master観測を入れる。
entry日masterは`entry_validation_only`で、decision featureへ入れない。
将来日に実際に約定したことをdecision時点の前提にしない。

予定sessionは既存calendarと時刻ruleによる`current_reconstruction`。過去のcalendar公開版が不明であることを明示し、
calendarを判断時点に取得済みだったとは主張しない。予定sessionはdecision featureや実約定とは別である。
日付不足・未対応sessionは引き続きBLOCKED。同日終値をfeatureに使わず、場中/引け後開示の候補は次の日次session。

`execution_outcomes.jsonl`だけがentry後のOHLC/出来高を読み、traded / no_observed_trade / price_unavailable / ambiguousに分類する。
OHLC・出来高・売買代金がすべてnullなら約定観測なしであり、停止理由までは断定しない。
部分欠損・矛盾・重複はambiguous。次の好都合な日への繰越しは行わない。
outcomeは研究行の採否・価格feature・entry日を変えず、`execution_claim=false`を維持する。

future outcomeはこのdecision lineageへ混ぜない。source間財務比較も、今回のmappingの観測日外へ主体対応を外挿しない。
